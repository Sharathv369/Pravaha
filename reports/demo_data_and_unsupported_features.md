## 1. Executive Summary & Core Ethical Directive

The user interface mockups generated by Google Stitch (`PRAVAHA_Stitch_UI_Reference.zip`) provide an aesthetically compelling, luminous design language. However, like many generative UI prototypes, they contain **fictional operational metrics, fabricated sensor telemetry, and simulated emergency response mechanisms**.

> ### Strict Scientific & Ethical Directive:
> **Never present demonstration data, placeholder telemetry, or uncalibrated confidence scores as real operational flood-warning intelligence.**
> In a disaster management interface, displaying fake live water levels, unverified shelter capacities, or simulated emergency dispatches violates engineering ethics and misleads evaluators.

This document classifies every data element and operational claim in the Stitch screens into four strict categories:
1. `VERIFIED DATA`: Grounded in real, verified USGS/NASA/GAGES-II datasets.
2. `AVAILABLE THROUGH EXISTING CODE`: Directly computable from our trained ML models or feature engineering modules.
3. `DEMONSTRATION DATA ONLY`: Fictional sample values hardcoded in Stitch HTML prototypes.
4. `UNSUPPORTED / NOT IMPLEMENTED`: Advanced operational features requiring external third-party infrastructure that does not exist in PRAVAHA.

## 3. UI Presentation & Guardrail Rules

To ensure complete transparency and prevent disqualification or confusion during hackathon evaluations, the frontend must enforce strict UI presentation rules:

### Rule 1: The "Truth Engine" Primary Mode
- The **Disaster Command Dashboard** and **Interactive River Intelligence Map** must be powered **100% by real verified data**:
  - Show the true count: **34 USGS Gauging Stations**.
  - Show true discharge units: **cubic feet per second ($cfs$)**.
  - Display actual historical hydrographs from `PRAVAHA_TRAIN_LABELLED.csv` and out-of-system predictions from `prompt_e_validation_predictions.parquet`.
  - Display real validation metrics: Overall RMSE ($82,871\text{ cfs}$), Peak RMSE ($155,137\text{ cfs}$), and $R^2$ ($0.4910$), clearly noting the LORSO out-of-system evaluation regime.

### Rule 2: Demonstration Banners & Visual Watermarks
- Any screen or component containing mock data (Alerts, Community Feed, NGO Logistics) must feature a persistent, prominent **`TruthBanner`**:
  ```html
  <div class="bg-amber-500/10 border border-amber-500/30 text-amber-800 px-4 py-2 rounded-xl text-xs flex items-center gap-2">
    <span class="material-symbols-outlined text-sm">science</span>
    <span><strong>DEMONSTRATION PROTOTYPE:</strong> This module illustrates future operational workflows. Data shown below is simulated for interface design demonstration.</span>
  </div>
  ```

### Rule 3: Simulated Interaction Feedback
- When a user interacts with simulated features (e.g., clicking *"Trigger Emergency Broadcast"* or *"Submit Hazard Report"*):
  - Do **NOT** simulate fake network success responses as if a real agency received the alert.
  - Display an explicit modal dialog:
    > *"Prototype Action Simulated: In a full deployment, this action would interface with local emergency dispatch services. No actual emergency alerts were dispatched."*

### Rule 4: Model Limitation Disclaimers
- On stations with extreme drainage areas (e.g. Mississippi River at Vicksburg, $1,144,500\text{ sq mi}$), the UI must display a **Model Extrapolation Badge**:
  > *"Extrapolation Boundary: Basin scale exceeds training distribution. Predictions utilize Specific Discharge ($q = Q/A$) normalization."*
